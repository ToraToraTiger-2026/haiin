## 既知の制限

| 項目 | 内容 |
|---|---|
| 自動提案は最適解ではない | 貪欲法。不足の大きい順に埋める。結果は、処理の順序や重みに左右される |
| チーム内の空きの重複 | 同じメンバーが複数のクライアントのチームに入っていると、チーム内の空きを重複して数える。「応援が必要な目安」は目安 |
| 計画需要を画面から編集できない | `plan_demand` は CSV / JSON でしか入れられない（需要入力の画面では、計画は固定で表示するだけ） |
| 祝日の自動判定がない | 祝日は、上限の例外（上限 0）を入れて表す。年ごとに登録が必要 |
| 配員ルールの期間が重ならない前提 | 同じメンバー・クライアントで期間が重なるルールは作れない。分けて入力する必要がある |
| 共有・同期ができない | データは1つのブラウザの中だけ。複数人での利用や、端末間の自動同期はない（JSON で手動で移す） |
| 認証がない | 「操作者」は名前の入力だけ。本人確認や権限の管理はない |
| JSON 取り込みの検査が浅い | `app` とテーブルの形だけ確認する。行の中身の形式は検査しない |
| JSON 取り込みが途中で止まる可能性 | 全削除してからテーブルごとに入れるので、途中でエラーになると、一部のテーブルだけが入った状態になりうる |
| DB の移行の仕組みがない | `DB_VERSION` は 1。構成の変更には、バージョンの更新と、移行の処理が必要 |
| 画面の表示件数の上限 | 配員ルール一覧は200件、変更履歴は200件、シナリオの比較は先頭30件など |
| CSP の設定がない | 外部のスクリプトを読まないので、現状は問題ないが、外部ライブラリを足すときは検討する |
| `.gitignore` が最小限 | バックアップ JSON・CSV を除外していない。リポジトリの外に保存する運用で防いでいる |
| 自動テストの仕組みがない | テストは、ブラウザで手動で開いて実行する。CI はない |

## 拡張の余地

コードや構成から見える、手を入れられそうなところ（計画ではなく、候補）。

- 計画需要の画面での編集。
- バックアップ JSON・CSV の誤コミットを防ぐ `.gitignore` の追加。
- JSON 取り込みの、行の中身の検査と、取り込みの途中失敗への対策（検査してから置き換える）。
- DB の移行の仕組み（`DB_VERSION` の更新と `onupgradeneeded` の移行処理）。
- 祝日の自動登録や、一括登録の入力の改善。
- 自動提案の改善（重みの調整、探索の工夫）。モードや優先度の考え方は [05-frontend-reference.md](05-frontend-reference.md) にまとめている。
- 自動テストの実行（コマンドラインやCIでテストを回す）。
